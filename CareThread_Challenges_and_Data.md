# Technical stuff I'd want his help on

So the care gap rules work by looking for specific medical codes in the data. Every condition, lab test, and procedure in healthcare gets a standardized code — like how every product at a grocery store has a barcode. Diabetes is one code, an HbA1c blood test is another code, a colonoscopy is another. My rules say things like "find all patients who have the diabetes code, then check if they also have a recent HbA1c code."

The problem I ran into is that there isn't always just one code for something. My first version looked for hypertension using code 38341003, which is what medical textbooks say. Synthea actually uses 59621000. Same disease, different code. About 40% of my initial gap detections were completely wrong because of this — the rules were searching for codes that simply didn't exist in my data, so they'd report "no blood pressure check on record" for every hypertensive patient, even ones who had plenty. I fixed the codes by looking at what Synthea actually generates, but in a real hospital system this would be way worse. Different EHR systems code the same thing differently, and some doctors just type free text instead of using codes at all. I want to ask him whether there's a better approach than manually listing out every possible code for each condition.

The LLM summary part has a hallucination problem. I tell the model "only use the data I gave you, don't make anything up" and it mostly listens, but not always. I built a script that checks the output afterward — did the brief mention a condition the patient actually has? Does the drug interaction alert match what my detection engine found? But the checks are pretty basic. They wouldn't catch the model saying "HbA1c is trending upward" when there's actually only one HbA1c value on record (you can't have a trend from one data point), or the model describing something as "severe" when the data doesn't say that. I want to ask what a more thorough checking system would look like.

The drug name matching works really well on my synthetic data (125 out of 126 medications matched). But that's because Synthea writes drug names in a clean, standardized way. A real medical record might say "pt's own insulin" or "metformin tabs" or misspell something or use a brand name that my system doesn't recognize. I have no idea how much the match rate would drop on messy real-world entries and I want his take on whether that's a solvable problem or a fundamental limitation.

The whole pipeline has only ever seen fake data. Synthea generates very clean, well-organized records. Real clinical data is messy — fields are missing, codes are inconsistent, some things are buried in free-text notes instead of structured fields. My rules and matching would almost certainly perform worse on real data, but I can't test that because I don't have access to any real patient records. I'd like to know if he thinks the synthetic-to-real gap is something judges will push on, and if there's a way to stress-test without actual patient data.

There's also a weird data quality issue. Some of the "conditions" in Synthea aren't really medical conditions. My best demo patient has "Received higher education (finding)" and "Not in labor force (finding)" listed as active conditions alongside her actual diabetes and hypertension. These are social observations that got coded using medical terminology, and right now the LLM just includes them in the clinical summary as if they're diagnoses. I need to either filter them out before they reach the LLM or teach the prompt to separate social observations from medical conditions.

Last one: the care gap rules assume the data is complete. If a patient actually got a mammogram but it happened at a different clinic and isn't in the records I have, my system flags it as overdue. That's a false alarm. In the real world this would happen constantly, especially for the exact population I'm targeting — FQHC patients whose records are scattered everywhere. The tool needs to be upfront about this and say something like "based on available records, this screening appears overdue" instead of stating it as fact. I'm doing some of this already but it could be stronger.

# And if he asks where real data would come from

Short answer: I don't have a clean solution yet, and I think that's worth being honest about.

Most states run something called a Health Information Exchange, which is basically a central hub that collects clinical data from hospitals and clinics across the state. Maine has one called HealthInfoNet, and it's actually one of the better ones in the country. In theory, a clinic could pull a consolidated patient record from HealthInfoNet before each visit. In practice, getting access requires formal agreements, the data isn't always complete, and the feeds aren't always current.

The other route is plugging directly into the clinic's electronic health record system. FQHCs typically use systems like eClinicalWorks, NextGen, or athenahealth. These systems now have to offer standardized APIs (the law requires it since the 21st Century Cures Act), so technically you can pull data from them. But getting certified to connect to even one EHR vendor takes months of paperwork and security reviews. And that only gets you data from one system — the ER down the road that runs a different system is a whole separate integration.

If I'm being realistic about how this would work as a product: you'd start with one clinic, connect to their one EHR, and prove that the tool is useful even on single-system data (catching gaps within their own records, flagging drug interactions, saving the doctor time). Then you'd expand to cross-system data through the HIE or additional integrations once you have a foothold. The record linkage piece I'm skipping in the demo becomes essential at that second stage, because that's when you have records from multiple systems that need to be matched to the same patient.
